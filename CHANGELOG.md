# Changelog

All notable changes will be documented here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## 1.0.0 - Unreleased

### Changed

- CLI: every host command moved under `wssp host`, with no aliases for the old names: `wssp connect` is `wssp host run`, `wssp login --slug` is `wssp host enroll --slug`, `wssp token login <ENV>` is `wssp host enroll --token-env <ENV>`, `wssp logout` is `wssp host logout`, and `drain`, `undrain`, `images`, `config`, `daemon quiesce`, `guard` and `tunnel` are `wssp host …`. The guard service entry `wssp-guard guard run` is now the internal `wssp-guard __wssp-guard` (re-run `sudo wssp host guard install --daemon-user <user>` to rewrite the unit; an already installed guard keeps working). On a machine that is not an enrolled host, `wssp host --help` lists only `enroll` (`--help --all` shows everything) and `host run`, `host drain` and `host undrain` exit 6 there unless given an explicit `--host-token-env`. Update systemd units to `ExecStart=%h/.local/bin/wssp host run --runtime incus` and `ExecReload=%h/.local/bin/wssp host daemon quiesce`.

### Added

- CLI: `ssh <name-or-id>.wssp` with plain OpenSSH (`ssh`, `scp`, `sftp`, `rsync`, `-L`/`-D` forwards, VS Code Remote-SSH, JetBrains Gateway), with no SSH keys or passwords. `wssp ssh-config [--install] [--rotate-host-key] [--json]` prints or installs a `Host *.wssp` block (`~/.ssh/config.d/wssp` plus one confirmed `Include config.d/wssp` at the top of `~/.ssh/config`) whose ProxyCommand `wssp ssh --stdio` speaks SSH on its own stdin/stdout over the connect plane with the wssp login (it never listens on a socket; any SSH auth is accepted, the user name is ignored). `wssp ssh <sandbox> [-- SSH-ARGS…]` runs the system ssh with the same options. Sessions map to `pty`/`exec` channels (`$SHELL -c` for commands, the guest `sftp-server` for the sftp subsystem), forwards to `tcp`/`unix` channels on the guest's loopback only; `-R`, agent and X11 forwarding are refused. One local ed25519 host key per install (`<user dir>/ssh/host_key`, kept by `wssp logout`). The session is not end-to-end to the guest: the server and the node see the bytes, as for shells. New Cargo feature `ssh` (on by default) adds russh (ring backend) and tokio, used only by `wssp ssh --stdio`; russh 0.65.4 is vendored under `third_party/` with a small patch so each SSH channel's input window grows only as its guest reads (a stuck channel stops only its own sender). See docs/guide/connect.md#ssh.
- CLI: `wssp sandbox forward <sandbox> <guestPort>[:<localPort>]… [--address IP] [--unix PATH]` forwards local TCP ports (or one 0600 Unix socket) to ports on the sandbox's own loopback over the connect plane: one WebSocket, one `tcp` channel per local connection (up to 32 at a time, a backlog of 32 beyond), half-close both ways, end-to-end flow control, refusals logged at most once a second. No host is ever named and no network path to the sandbox is opened. Ctrl-C exits 130; a wssp-side end (revoked login, stopped sandbox) resets every local connection and exits 125. Same scope as `shell` (`sandboxes:connect`). See docs/guide/connect.md#port-forwards.
- Node daemon and relay: `tcp` and `unix` channel kinds (hello `channels.kinds`). The guest channel helper, run as the guest user in the channel's own scope, connects to guest `127.0.0.1:<port>` (then `[::1]`) or an absolute guest Unix socket over `incus exec` and relays a framed byte stream; a refused connect exits the channel with the new error code `connection_refused`. Rollout: server first, then daemons (an older node is refused `unsupported_capability`).
- CLI: `wssp sandbox shell <sandbox> [-- COMMAND…]` opens a shell or runs a command in a sandbox over the new connect plane (`GET /v1/sandboxes/{id}/connect`, `wssp.connect.v1`). With a terminal it allocates a guest tty (raw local terminal, restored on every exit; window resizes follow); otherwise stdout and stderr stay separate, stdin and its EOF are piped, and Ctrl-C, SIGTERM and SIGHUP become remote signals. It exits with the remote status (128 + N for a death by signal N), keeps the `/v1` exit codes for refusals, and exits 125 naming why when wssp ends the session. Needs `sandboxes:connect` (write `wssp login`); older logins must log in again. See docs/guide/connect.md.
- Node daemon and relay: CLI channels (`channel.*` relay frames, hello capability `channels`). Each channel is one guest process (`pty` or `exec`) in its own guest systemd scope, with end-to-end credit, a guest-attested exit status bound to a per-channel secret, signals, sshd close semantics (normal close hangs up; revoke, lifecycle and relay loss kill the scope with proof) and a durable registry the next daemon start sweeps. Guests need systemd 254 or later for channels. The client route and `wssp sandbox shell` follow. See docs/design/connect-channel-contract.md.
- CLI user side: `wssp login` (device flow with scope `user-login`; the browser approval chooses the key's name, read or write access, pools, own-sandboxes-only, live sandbox limit and expiry), `wssp logout` (self-revokes with `DELETE /v1/key`; `--local` skips the server), `wssp whoami`, `wssp sandbox create|list|get|exec|ps|logs|stop|start|destroy`, `wssp sandbox files ls|stat|read|write|mkdir|mv|rm`, `wssp sandbox ports get|expose|set|close|link` and `wssp template list|get`, all with `--json`. The login is saved at `<data_dir>/user/login.json` (0600) apart from host state; CI uses `WSSP_API_KEY` with `WSSP_SERVER`. New exit codes: 7 not logged in or 401, 8 forbidden, 9 limit reached, 10 conflict, 11 retryable, and for `sandbox exec` 125 (wssp failure or unknown outcome) and 130 (Ctrl-C); `sandbox exec` otherwise exits with the guest command's exit code. See docs/guide/cli.md.
- Owner-scoped Incus KVM sandboxes on enrolled Linux hosts, with host pools and capacity-aware placement.
- Native HTTP API and TypeScript SDK for commands, streamed output, files and resumable transfers.
- Localized web dashboard with browser terminals and PWA support.
- VM template builds from JSON recipes or a supported Dockerfile subset, plus capture and image distribution.
- Open egress by default behind a node nftables guard, with optional destination allowlists.
- Write-only CLI-login credential vault and signed webhooks.
- Linux CLI and outbound node daemon, shell installation from GitHub Releases, and server and worker images on GHCR.
- Committed schema migrations and a guarded Prisma Migrate runner with delayed removals and backup/restore commands.
- Static musl Linux CLI binaries for x86_64 and ARM64.
- Node 26.13.1 runtime and pnpm 12.18.0 tooling.
