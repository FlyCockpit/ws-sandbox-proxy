# Web shell rules

## Shell rules

Four rules every page meets, in both themes and at every width. `pnpm policy:checks` enforces what a static check can (rules G8 and G9 in `scripts/check-web-conventions.ts`, gate 4 of `scripts/check-agent-rules.ts`; G10 is § Viewport scale), `apps/web/src/components/public-shell.test.tsx` and `apps/web/src/lib/theme-contrast.test.ts` pin the markup and the tokens, and `pnpm check:layout` measures the geometry in a browser (§ Layout check).

1. **A footer sits at the bottom of a short page.** wssp has no site footer today: the landing is the only public page, and the app shell has the BottomNav on phones. The public shell (`apps/web/src/components/public-shell.tsx`, used by the `_public` layout and the 404) already lays its `<main>` out as one `flex min-h-full flex-col` column whose routed page grows (`flex-1`), so a footer added later goes once, as that column's last box: on a short page its bottom is then the scroller's bottom, on a long page it follows the content. No `position: fixed` footer, no `min-h-svh` layout, no second scroller, and no `<footer>` in a route file (a `<footer>` inside an `<article>`, `<section>` or similar sectioning element is that element's own and stays). A page that should fill the remaining height (a centred empty state, the 404) uses `flex-1`.
2. **Full-bleed dividers span the viewport.** The headers' `<hr>`, the admin section nav's `border-b` and full-width banners (the 2FA banner) reach the viewport's right edge at every width, from the start of their column: 0, or the dashboard content column's left edge next to the desktop sidebar. On a page that scrolls, rules inside `<main>` meet its visible scrollbar, which sits at that edge, as on any scrolling page. That is why neither `<main>` reserves a scrollbar gutter: with classic scrollbars (Windows, Linux) a stable gutter is an empty 15px strip that every rule inside the scroller stops short of, even when nothing scrolls. The cost is that centred content moves by half a scrollbar when a page grows past the viewport on those platforms; overlays don't cause it, because the overlay scroll locks (Base UI, vaul) lock the document, not `<main>`, and nothing toggles `overflow-y` on `<main>`. A bounded nested pane (a terminal, a table) may still reserve its own gutter.
3. **No surface ignores the theme.** The theme is the stored choice, else the OS, applied as the `.dark` class before first paint (`packages/config/src/theme-init.ts`). Every surface (toasts, banners, popovers, menus) uses the tokens in `packages/ui/src/styles/globals.css` and `dark:` variants, never a `prefers-color-scheme` query or a literal colour; a new colour becomes a token there. A colour that is deliberately not a theme colour (a QR code, a mask, a colour derived from `currentColor`) carries a `theme-exempt: <reason>` comment on its line or the line above, as the vendored `packages/ui/src/styles/shadcn-tailwind.css` masks do; `url(#id)` references are not colours. Toasts are a popover surface: `globals.css` fills sileo's pill with `--popover`, writes the title in `--popover-foreground` and maps sileo's state colours to `--state-*`, `--destructive` and `--primary`, and the Toaster (`packages/ui/src/components/sileo.tsx`) gets no `theme` prop (sileo's themes invert the page). Text and state colours reach 4.5:1 on the surface they sit on in both themes.
4. **Every route renders inside a shell, the 404 included.** An unknown URL matches no layout, so `$lang`'s `notFoundComponent` (`PublicNotFoundPage`) wraps the not-found body (`components/not-found-page.tsx`) in the public shell: header with language and theme controls, scroller. A `notFound()` thrown by a route without its own `notFoundComponent` lands on the same public 404, which is how hidden admin pages answer (`lib/hidden-admin.ts`): an app-shell 404 for `/admin` next to a public-shell 404 for an unknown URL would reveal that `/admin` exists.

## Viewport scale

The app grows with the screen above 1920 CSS px, so a 4K monitor at 100 % OS scaling shows the same layout as a 1080p one instead of a small island in the middle. Phones, laptops and 1080p screens are unchanged. Same rules as the template (FlyCockpit/template, its design system's Viewport scale section).

1. **One root rule scales everything.** `html` in `packages/ui/src/styles/globals.css` sets `font-size: clamp(100%, calc(100% + (max(100vw, 100vh) - 1920px) / 240), 150%)`. The root is the browser default (100 %, so a user's own default font size is respected) up to a 1920 CSS px long side, then grows 1px per 240px, capped at 150 % of that default. With the usual 16px default that is 24px at 3840, and it stays there; a larger default gets the same +1px per 240px on top (20px → 28px at 3840, capped at 30px). The long side makes a portrait 2160×3840 screen scale like a landscape 3840×2160 one; 4K at 200 % OS scaling is 1920 CSS px, so it is unchanged. Media queries use the browser default, so breakpoints don't move, and browser zoom still enlarges. `apps/web/src/lib/viewport-scale.test.ts` pins the rule.
2. **Sizes are rem, not px.** Type, control heights, padding, page widths, dialogs, sheets, cards and images use Tailwind's rem scale, so they follow rule 1. A px size does not scale: next to rem siblings it ends up too small at 4K (a px switch track around a rem thumb overflows). px stays for hairlines and borders, shadows, radius offsets, touch-target floors (`min-h-[44px]` is a minimum, not a size) and the minimum widths of tables that scroll inside their card.
3. **Text is at least 12px** (`text-xs`, 0.75rem) at every width, labels, badges and the terminal key hints included; 18px at 3840. A BottomNav label that doesn't fit ends in an ellipsis (the tab's accessible name stays whole); tabs shrink to the 44px touch floor, in px so a large browser font size can't push five tabs past a 320px screen. Rule G10 in `scripts/check-web-conventions.ts` (`pnpm policy:checks`) rejects, in any string in web source (className, cva() variants, constants, other class props), in `text-[…]` or `[font-size:…]`, a px font size (`text-[13px]`) or a px branch in an expression (`max(100px,0.75rem)`), a rem size below 0.75, an em size below 1 or a % size below 100 (they drop under 12px inside 12px text), a viewport unit (`text-[2vw]`) and any other size expression without a 0.75rem floor; `text-[length:max(0.9em,0.75rem)]` passes.
4. **Pages use the width tiers.** `PageShell`'s `narrow`, `default` and `wide` (`apps/web/src/components/page-shell.tsx`) are rem, so they scale with rule 1. Every signed-in page sits in `DashboardFrame`'s content column, which is the `wide` tier (`PAGE_COLUMN_CLASS`, 80rem: 1280px up to 1920, 1920px at 3840), the same column as the admin section nav and the banners. Card grids add columns when the column has room (the Settings hub: one, two, then three from `xl`; admin observability counters: as many 10rem tiles as fit). Dense tables scroll inside their card, never the page.
5. **Full-bleed bands keep their content in the page column.** The background and border span the content area (rule 2 of § Shell rules); the content goes in `PAGE_COLUMN_CLASS`, so the 2FA banner's message and its Set up 2FA action sit together instead of 3000px apart at 4K, and line up with the page below.
6. **Long copy gets `max-w-prose`** (45-75 characters per line): `PageHeader`'s description carries it, as do the banner text and the admin settings recovery note.
7. **The header stays full width**; its row scales with rule 1.
8. **The page column is only as tall as what is left under a banner.** `PullToRefresh` (`apps/web/src/components/pull-to-refresh.tsx`, the template's component) wraps the column with `display: contents` and floats its indicator over the page, so a banner above the column never makes `main` scroll. A region that owns its vertical gestures (the terminal panel) carries `data-pull-to-refresh="off"`. A gesture counts as a pull only once it has moved 10px mostly downward; a mostly sideways start (SelectorRow, carousels) never refreshes.

## Shared controls

Contracts the shared components in `packages/ui/src/components` keep, pinned by `apps/web/src/lib/theme-contrast.test.ts` and the tests in `apps/web/src/components/shared-ui/`.

- **Field outlines reach 3:1.** `--input` (input, textarea, select, checkbox and the Off switch track, `data-unchecked:bg-input` with no alpha) reaches 3:1 on background, card, popover and muted in both themes. `--border` stays decorative. A light field never takes an `--input` tint (`bg-input/30` buries the placeholder); a search field in a menu or picker (`CommandInput`, the async comboboxes) uses an opaque `bg-muted` fill in both themes with an explicit `placeholder:text-muted-foreground`, because Tailwind's default placeholder is the text colour at 50% (4.23:1 on the dark `bg-input/30` fill). A dark hover fill stays at `dark:hover:bg-input/35` or lighter, where a muted placeholder still reaches 4.5:1 (at /50 it fell to 3.78:1 on a card).
- **Copy controls.** `CopyField` and `CodeSnippet` write code in `font-mono text-xs leading-5`. The copy button has its own 44px column beside the text and never covers it. A long value scrolls inside its box and fades out at the edge with more to scroll. `CodeSnippet wrap` wraps long lines instead, for commands that must be read in full on a phone and for logs.
- **Edge fades are measured.** `SelectorRow`, `CopyField` and `CodeSnippet` set `data-overflow-start` / `data-overflow-end` with `useScrollEdges` (`packages/ui/src/hooks/use-scroll-edges.ts`), and the `edge-fade-x` mask in `globals.css` fades only those edges. Do not use the vendored shadcn `scroll-fade-x`: without scroll-driven animations it fades both edges even when nothing overflows. A focused `SelectorRow` item scrolls clear of the fade (instantly under reduced motion).
- **Toasts stack and fit the pill.** The `toast` facade (`sileo.tsx`) gives every toast its own id, so two toasts stack instead of merging. A message that would be cut off in the pill goes into the description, under the translated short title from `AppToaster`. The facade measures the title at its real font and root size (`titleOverflowsPill`), because a short message of wide glyphs, or any message on a large screen where the root font grows, can overflow while a character count says it fits. `globals.css` caps the header row at the pill's width and ellipsises the title, so the badge icon stays inside the pill. The description and the action button text are `--popover-foreground`, which reaches 4.5:1 on the pill and on the button's tints.
- **Menus show the current choice on an opaque surface.** The theme menu (`apps/web/src/components/mode-toggle-menu.tsx`) uses radio items bound to the stored theme. `DropdownMenuContent` is opaque `bg-popover`, with no translucency or backdrop blur.

## The signed-in home

Signing in, verifying an email, the app name in the header and "Open app" all land on the main list, Sandboxes (`APP_HOME` in `apps/web/src/lib/app-home.ts`), not on a stats page. `/{lang}/dashboard` is redirect-only (`routes/$lang/_app/_auth/dashboard/index.tsx`), and `safeRedirectTo` falls back to `APP_HOME`.

The home carries a getting-started checklist (`components/sandboxes/onboarding-checklist.tsx` over the generic `components/home/getting-started.tsx`, logic in `lib/getting-started.ts`): somewhere to run, a template, a first sandbox. It sits above the status filter whatever the filter shows. Every step's done state comes from a bounded read, never a tick by hand; once a sandbox exists (deleted ones count) the checklist is done for good and its step reads stop. It shows "n of m done", each open step's next action (a step waiting on an earlier one says so instead of offering a dead button), is a disclosure collapsed below `sm` (the list stays on screen on a phone), and can be hidden early with an Undo toast. The hidden flag is per user and per browser (`localStorage`, `wssp.getting-started.hidden.<userId>`).

## Public header

Public pages (the landing page and the 404) stay static: no session lookup, no Better-Auth chunk. Only the header's last action follows a presence-only session-cookie hint (`getSessionCookieHint` in `apps/web/src/server/auth-session.ts`, shared as one query by `apps/web/src/lib/session-hint.ts`): "Open app" to `APP_HOME` when a Better-Auth session cookie is present, Sign In otherwise, in one box as wide as the longer label, a 44px icon below `sm`. The `_public` layout seeds the hint during SSR, the landing redirect reads the same entry, the 404 asks on the client, and the `_auth` gate writes what it learned. The hint is never an access check: a stale cookie only sends the visitor to `APP_HOME`, whose gate sends them to sign in. `apps/server/src/ssr-cache.ts` never caches a request carrying the cookie.

The landing page's actions follow the sign-up mode (`apps/web/src/lib/signup-mode.ts`): open shows Create account and Sign in; bootstrap (sign-up closed, `ADMIN_EMAILS` set, no active administrator yet: `appConfig.adminBootstrapSignupEnabled`, see `packages/api/src/lib/admin-presence.ts`) shows "Set up this server" first; closed shows Sign in and the invite-only line; a tab holding a pool invitation (`apps/web/src/lib/pool-invite.ts`) counts as open. The header's Sign Up ("Set Up" in bootstrap), the sign-in page's line under the form and `/signup` read the same mode; a closed `/signup` renders an invite-only card instead of redirecting.

## Logo slot

Both header rows start with `AppNameLink`: the logo, then the name. The logo is an `<img>` with its 32px box declared (`APP_LOGO` in `apps/web/src/lib/app-logo.ts`, 32/64/128 px sources with `sizes="48px"`, the largest width the slot is drawn at on a scaled-up root; `sizes` resolves `rem` against the initial font size, not the scaled root), `alt` = the app name and the visible name `aria-hidden`, so the link is named once. The files are generated from `apps/web/assets/logo.png` with the favicon and install icons (`apps/web/pwa-assets.config.ts`, `pnpm --filter web generate-pwa-assets`, outputs copied to `apps/web/public/`). The artwork has its own dark outline and keeps its shape on both header backgrounds, so it needs no plate.

## Layout check

`pnpm check:layout --url <web dev server>` (`scripts/check-layout.ts`) opens the landing page, the 404 and the sign-in page at 390×844, 1280×800, 1440×1600 and 390×300 in agent-browser's headless Chromium, which draws classic scrollbars, and fails when the document scrolls, a page is outside a shell, `<main>` reserves a gutter, or a full-width rule stops short of its edge. It also raises the file-drop toast with the stored theme light, then dark (the OS set to the other one), and fails when the toast is not filled with that theme's `--popover` or its title, badge or action is below 4.5:1. With the seeded accounts' credentials file (`--accounts <file>` or `WSSP_CHECK_CREDS_FILE`, § Dialog fit and shell loading checks) it signs in as the admin and adds the dashboard (2FA banner) and the admin users page (sticky section nav); without it those are skipped. It measures page by page (every viewport of one page, then the next), so the admin signs in once, and before each probe it waits up to 8s for `<main>` to show no loading marker (`data-slot="skeleton"` or `aria-busy="true"`) and stop growing: loading UI must use `Skeleton` or `aria-busy`, or this wait cannot see it. A page that never settles fails as "still showing a loading skeleton" or "kept changing". It needs a running `pnpm dev` (web and server) and agent-browser on the PATH, so it is not part of CI; `pnpm check:layout:test` (in `verify:tooling`) covers its judge.

## Form surfaces

Where a create or edit form lives is decided by its length, not by habit. A tall dialog that scrolls inside itself hides the action button and the errors below the fold, and on a phone it is a scroller inside a scroller.

- **A dialog is for confirmations and short forms only:** about six controls or fewer, and it fits **without inner scrolling** at 1280×800 and 390×844 (`pnpm check:dialogs`, below). `DialogContent` is capped at the visible viewport with one inner scroller (`data-slot="dialog-body"`, padding and gap via `bodyClassName`), and `DialogHeader`/`DialogFooter` are sticky, so even a dialog that grows never hides its title or actions; `AlertDialogHeader`/`Footer` are sticky too.
- **Anything longer is a page or a wide side sheet,** using the width: sections with headings, two columns of fields from `lg:`, one on phones.
  - **A page** (`FormPage` from `@wssp/ui/components/form-page`, its own route such as `/dashboard/sandboxes/new`, `/dashboard/templates/new/build`, `/settings/webhooks/new`): deep-linkable, the back button works. It renders inside the dashboard frame's content column (pass `className="px-0 pt-0"`, the frame already pads), its title row sticks to the top and its action bar (`FormActionBar`, one right-aligned row, primary action **last**) to the bottom of `<main>`. A live summary of what will be created goes first in the action bar (`components/form-page-status.tsx`).
  - **A wide side sheet** (`<SheetContent size="wide">` + `SheetHeader` + `SheetBody`, the one scroller, + pinned `SheetFooter`, primary last; `components/wide-sheet.tsx` wraps them): for editing in context. Every sheet with a form uses `SheetBody` and `SheetFooter`; the popup itself never scrolls.
- **The quick path first.** Up front the few fields most people must decide, with safe defaults; expert fields go in collapsed `AdvancedSection`s (native `<details>`, fields stay mounted), named by topic, each showing a one-line summary of its current values while closed. Consecutive Advanced sections join into one ruled list when they are siblings in a `space-y-8` column (a `FormPage` body, a `WideSheet` body, or a wrapper `div` inside a `FormSection`). A `FormSection` whose content is one wide control passes `gridClassName="lg:grid-cols-1"`.
- **No raw configuration.** Key-value pairs use `KeyValueEditor`, never a JSON textarea; every enum, scope and option has a human label (`FormSelect` maps values to labels in the closed trigger); pickers replace free text.
- **Errors inline, focus on the first invalid field** (`focusFirstInvalidField` from `@wssp/ui/lib/focus-first-invalid`; it opens a closed `AdvancedSection` first), never only at the bottom or in a toast.

The components in `packages/ui` (`form-page.tsx`, `key-value-editor.tsx`, `range-field.tsx`, `lib/dotenv.ts`, `lib/range-scale.ts`, `lib/focus-first-invalid.ts`) are identical copies of the template's; change them there first. Their strings come from `apps/web/src/hooks/use-form-field-labels.ts` (`common:forms.*`).

### RangeField

For numbers people tune by feel (vCPU, memory, disk): a slider with a number input beside it, wired to a TanStack-style `field` holding the base unit. `stops` make the slider move stop to stop (vCPU 1, 2, 4 … 32); `scale="log"` spreads a wide range (disk); `units` format the value (memory is stored in MiB and shown in GiB). A typed value is committed on blur or Enter: above the limit or `max` it becomes the highest allowed value, off `step` the nearest step, each with a notice. `defaultValue` draws the default tick and offers Reset; `limit` + `limitMessage` cap the slider to what the chosen host or pool can take. The Create sandbox page (`components/sandboxes/create-sandbox-parts.tsx`) adapts it to "untouched = inherit": the field shows the pinned version's value, choosing that value (or Reset) sends nothing, Latest shows no default mark, and while a pooled create waits for capacity the cap is shown but not applied.

### KeyValueEditor

Edits `{ key, value }[]` (envs, labels, build args): rows, a `.env` text mode, paste-a-whole-`.env` into a key field, and file import. Lines that don't parse are kept verbatim as flagged rows and block submit; multi-line values (certificates) keep their line breaks; `secret` masks values. Block submit with `hasKeyValueErrors(entries, { reservedKeys, keyPattern })`. The editor's default key rule accepts `__proto__`, so wssp always passes `PROTOTYPE_NAMES` (`apps/web/src/lib/key-value-entries.ts`) in `reservedKeys`, and turns entries into an API object with `entriesToRecord` (null prototype, blank rows dropped, values exactly as typed). Page state that is not a TanStack field goes in through `stateField`, whose errors show under the editor and mark it invalid for focus.

## Route pending states

On a hard refresh of a signed-in page, what paints first is already the app: the same header, sidebar and bottom nav as the loaded page, with only the **content area** as a skeleton shaped like that page. The `_app` layout is `ssr: false`, so the server renders its pending component (`AppShellPending` in `components/app-shell.tsx`: the shell's own `AppShellFrame` around `ContentSkeleton`) and the client keeps it until the layout mounts. Every pending boundary below it (the router's `defaultPendingComponent`, `_auth`'s session check inside the live dashboard frame) renders `RouteContentSkeleton` (`components/route-content-skeleton.tsx`).

Each route declares its shape in `staticData` (`apps/web/src/lib/pending-layout.ts`): `pendingShape` (`list`, `detail`, `form`, `dashboard`, `hub` for the Settings hub's card grid, `auth` for the sign-in card) and `pendingWidth` for unframed pages; `_auth` sets `pendingFrame: "dashboard"`, so pages inside it get the sidebar from the first frame. A new route sets its `staticData`; a new layout with its own chrome adds a `PendingFrame` and draws it in `route-content-skeleton.tsx`. Admin routes declare only the defaults: /admin's first frame must equal any other unframed URL's, so it never reveals that /admin exists. `components/public-shell.test.tsx` pins that the pending frame and the loaded frame are the same markup outside `<main>`; the header carries `data-app-header` for the check below.

## Offline

`navigator.onLine === false` is a reliable hint; `true` only means a network interface is up. `apps/web/src/lib/network-failure.ts` classifies a failure as `offline` (browser offline, no HTTP answer) or `unreachable` (online, the fetch itself failed), and `friendly()` maps both to copy that says what to do.

- **Banner.** Both shells render `OfflineBanner` under the header, in the header's grid row, so it never covers the page or the BottomNav; `AppShellPending` renders it too. Its live region is always mounted. Offline it says how old the shown data is; on reconnect it says "Back online." for a few seconds (`lib/connectivity-notice.ts`), then empties.
- **Writes.** `lib/offline-mutations.ts`, installed in `router.tsx`, gives every mutation `networkMode: "always"`: offline, the request fails at once and the global toast says "You're offline…", instead of TanStack pausing it with a spinning button. A replay-safe write may opt into `meta: { offline: "queue" }`: it waits, with a toast, and another one when it is sent. Queued writes live in memory only. The `onlineManager` starts from `navigator.onLine`.
- **Reads.** An offline query error never toasts. `QueryBoundary` shows "This will load when you reconnect" for a first load TanStack paused, uses that copy for an offline error, and still keeps retained content. `ErrorState` shows an offline page without Reload and retries on reconnect (`hooks/use-retry-on-reconnect.ts`); an online fetch failure says the server could not be reached.
- **Imports.** A route chunk that failed offline is not a stale build: `useRouteImportFailure` and `useStaleBuildRecovery` never load a document for it, and the router's own render-time reload is suppressed.

## Query cache follows identity

The TanStack Query cache, Zustand stores (the orphan-credential warnings), module state and every in-flight request callback belong to one identity: the one the document was used by. `apps/web/src/lib/document-identity.ts` keeps that identity at module scope for the whole life of the document (never in a component, which an unmount or an error reset would make forget). When a confirmed identity differs from it, the document is replaced with a full load. A page load is asynchronous, so every replacement first quarantines the document synchronously: the page is hidden (`display: none !important` on the root, which no descendant can undo) and the QueryClient sealed (emptied, and anything a late callback adds is removed again) and the orphan-credential store cleared (`router.tsx`), so nothing of the previous identity stays on screen while the new page loads.

- **Explicit sign-out** (account menu, MCP "sign in again"): `signOutAndLeave()` (`apps/web/src/lib/explicit-sign-out.ts`) marks the sign-out, and only after the server confirmed it `leaveDocument()` to localized login, a fresh document with an empty cache. A failure (returned or thrown) undoes the mark and keeps everything; add any new sign-out button through it.
- **Signed out elsewhere** (another tab, expiry, revocation): the document reloads in place; the guards send the visitor to login.
- **Another account** (same tab or another tab): the document reloads in place; the guards admit the new account and its queries load fresh.
- **Anonymous → signed in**: nothing; an anonymous cache holds only public data.
- **`pending` / `error`, or an offline, degraded or refetching answer**: never acted on; a flaky session check must not reload a signed-in page.

Three observers feed it, and none can be skipped:

- **Every session guard** uses `apps/web/src/lib/route-session.ts` (`resolveRouteSession()`, `resolveProtectedRouteSession()` for `_auth`, `resolveRouteAdminAccess()` for `/admin`): the server probe, then the identity check. A different identity replaces the document and the guard never settles, so no page renders the previous identity's cached data, even for a switch the watcher did not see. `pnpm policy:checks` rejects any route-file reference to the bare probes or to `@/server/auth-session` / `@/server/admin-route-access`.
- **The root identity boundary** (`components/identity-boundary.tsx`, enabled from the first account-aware page and kept mounted across public pages) runs `useReloadOnIdentityChange()` in a layout effect, before a frame pairs the new chrome with the old data. It also connects the open tabs: Better Auth tells other tabs about a sign-out but not a sign-in, so every session change made in a tab (Better Auth's session signal, `lib/auth-client.ts`, before the flow navigates) and each newly confirmed identity (watcher or guard) is announced on the document's `BroadcastChannel`, and every other tab with a watcher re-checks its session.
- **The global error toasts**: before any toast opt-out, a query rejected with 401 asks Better Auth to check the session (one check in flight at a time) instead of toasting; a mutation still toasts. Nothing toasts once the document is being replaced.

Until a guard has admitted anyone, no chrome shows an account. The `_app` shell's pending state (`AppShellPending`) paints before any guard ran, while Better Auth's atom may still hold the previous account; it renders under `SessionUnconfirmed` (`apps/web/src/lib/session-unconfirmed.ts`), where `useAuthSession()` reports `pending`. The same mask holds while another tab's announcement (or a 401) is unchecked here: every announcement and every 401 that starts a check bumps a verification generation, and the identity is held unverified when no watcher is connected (before the root boundary first mounts, or while the first navigation into the app is still loading; the document's channel opens as soon as Better Auth's client loads, so a public page that reads the session, such as the language menu, never misses one), when the watcher's check gets no settled answer (failed, or still superseded after its follow-ups; the boundary stays mounted across public pages, so no remount would check again), and from the start of the watcher's check while a public page is showing (so an app page entered meanwhile shows no account), or once the visitor leaves the account pages while such a check still runs. On an account page the chrome already on screen stays until the check answers, so tabs don't flicker each time another tab confirms its identity. While unverified, `useAuthSession()` reports `pending` until a fresh check confirms this document's identity or replaces the document: a guard's server answer (generation taken before its probe), or a check the watcher starts (on mount, retried on focus, visibility and reconnect; one superseded by another session fetch is followed up at most 3 times, 250 ms apart; all dropped on unmount). Only a settled, successful answer (or a 401) counts, and one asked for before a newer invalidation never does, so a guard error or an unguarded page (verify-email, mcp-login) never shows the stale account. The chrome also never shows another account than the one this document was admitted as (`documentIdentityBaseline()`, a user or confirmed anonymous): an atom still holding an account read before any guard ran (a public page's language menu) whose refresh failed since reports `pending` until it catches up or the watcher replaces the document, and orphan-credential ownership follows the admitted account too. When the atom's account disagrees with the admitted identity and is not a fresh answer (retained by failed or running refreshes, or inherited from before the boundary mounted over an anonymous admission), the watcher holds the identity unverified and checks it like any other, whenever that mismatch appears; a fresh other account still replaces the document at once, and a sign-in over anonymous is adopted. A session fetch still running when anonymity is admitted (at every anonymous admission, a repeat included; asked before it, say before a revocation) is superseded by the watcher's own check rather than adopted as a sign-in. While unverified, the watcher's reactive observer never adopts the atom's snapshot, only its own checks' answers. The watcher and bookkeeping that never paints (`useOrphanOwnerSync`) read the session unmasked (`useAuthSession({ unmasked: true })`); the anonymous-only forms latch their first settled answer (`useAuthSessionSettled`), so a mask never unmounts what was typed; the boundary is enabled by the router's matches, never by the session, so the mask cannot keep it from mounting.

The router also covers the back/forward cache: a document that ever held a signed-in user's state is hidden as it enters the cache and reloaded when restored, so Back never shows a frozen page nobody re-checked. Anonymous pages are cached as usual.

Why a full load, not `queryClient.clear()` or a fresh `QueryClient`: clearing the cache while observers are mounted cancels their fetches silently and can leave a page stuck on a skeleton, `resetQueries()` refetches active queries as the wrong identity, and neither stops an in-flight mutation whose late `onSuccess` writes the old identity's data back. A swapped client still leaves Zustand stores and module state behind. Persisted browser storage holds no private data: the localStorage stores are device preferences, the getting-started flag's key carries the user id, and the service worker caches only static assets. A new store that persists private data needs its own identity scoping.

## Dialog fit and shell loading checks

Both need agent-browser and a running stack (wssp has no mock mode), so they are not part of CI. Point them at it with `WSSP_CHECK_URL` (or `--url`) and `WSSP_CHECK_CREDS_FILE` (or `--accounts <file>`), a KEY=value file with the seeded accounts (`ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_TOTP_SECRET`, `USER_*`), read at run time and never committed; add `--no-sandbox` on Ubuntu 23.10+.

- `pnpm check:dialogs` opens every dialog in `DIALOGS` (`scripts/browser-checks.config.ts`) at 1280×800 and 390×844 and fails when the popup or anything in it scrolls, when it reaches outside the viewport, or when it does not open (`--only "<name>"` runs one). Add every new dialog there; a dialog that cannot fit becomes a page or a wide sheet and leaves the list.
- `pnpm check:shell-loading` hard-reloads the `SHELL_PAGES` on a throttled network and CPU, stored theme dark and OS light, records every frame, and fails when the first painted frame lacks the header, `<main>` or bottom nav or is not the content skeleton, when the header, bottom nav or top of `<main>` moves before the page has loaded, when a frame is in the other theme, or when layout shift exceeds 0.05 (on a page whose content does not fit the viewport, a shift that only pushed a public footer (`[data-public-footer]`) below the first screen does not count; wssp renders no such footer today, so this rule and "a page that fits shows its footer" are inert until one exists).

The checks sign in through the real form (`formSignIn` in `browser-check-lib.ts`): the password and the code go to the page over stdin, the second factor's code is computed from `ADMIN_TOTP_SECRET`, and every wait after the submit is one short evaluation at a time (`pollPage`). A sign-in ends in a full page load (`window.location.assign`, the identity boundary), which cuts off any script still running in the old page, so a check never runs a long in-page loop across a navigation. A `pollPage` probe returns a plain value (a string means done, anything else means look again); agent-browser already JSON-encodes it once. A script read through `evalJson` returns `JSON.stringify(...)`, because `parseEvalOutput` parses it twice. Each run uses its own agent-browser session, `<check>-<pid>`, behind an optional `BROWSER_CHECK_SESSION_PREFIX`, so runs in parallel (two checkouts, two agents) never share a browser. A missing precondition ends a run with one `stopped: …` line or a case's "it needs …" hint (a running sandbox, a pool, an API key), not a stack trace.

`scripts/check-dialogs.ts`, `scripts/check-shell-loading.ts` and `scripts/browser-check-lib.ts` follow the template's (wssp keeps a wait before each dialog step and records no cookie consent); `browser-checks.config.ts` is wssp's. Their judges, `pollPage` and `formSignIn` have unit tests (`pnpm check:dialogs:test`, `pnpm check:shell-loading:test`, in `pnpm verify:tooling`).
