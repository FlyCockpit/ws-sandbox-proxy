# Sitemap

Current routes for the web app (`apps/web/src/routes/`).

Every URL is prefixed with a locale segment — `/{lang}/...` where `{lang}` is
one of the supported BCP 47 tags (currently `en-US`, `es-MX`). Visiting an
unprefixed path or an unknown locale 302s to `/${DEFAULT_LOCALE}/...`.

## Public Routes

Only indexable content pages belong in `apps/server/src/seo.ts` `PUBLIC_PATHS`
for `/sitemap.xml` and `/llms.txt`. Auth routes below are public in the router
sense, but excluded from SEO discovery.

A visitor with a session cookie is redirected to `/{lang}/dashboard/sandboxes` (presence-only hint, no session lookup); actions follow the sign-up mode (Create account · Set up this server · Sign in). |

## Authenticated Routes

All require an active session. Most use the `_auth` layout; `/device` uses `_app` with its own verified-owner and 2FA gate. Its unprefixed `/device` entry redirects through the locale layout, preserving `user_code`.
An anonymous visitor to an `_auth` route is sent to `/{lang}/login?redirectTo=<the full intended path>` and returns there after sign-in (`loginRedirect` in `apps/web/src/lib/route-session-access.ts`, `safeRedirectTo` in `apps/web/src/utils/safe-redirect.ts`). Every dashboard page reads its data through an owner-scoped, 2FA-gated `protectedProcedure`.

## Agent and MCP routes

These locale-prefixed pages are non-indexable and excluded from `PUBLIC_PATHS`,
`/sitemap.xml` and `/llms.txt`. MCP consent/login entry pages redirect a signed-out
person through login and back; consent and credential management require an
active owner session and the required account/2FA policy.

| Path                            | Description                                                                                                                                                                                                                                    |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/{lang}/settings/agent-tokens` | Authenticated token mint/list/revoke (preset, custom or no expiry, within operator limits), MCP connection instructions, connected OAuth apps and grant revocation. Own sandboxes only defaults on; host scopes carry the Incus-admin warning. |
| `/{lang}/mcp-consent`           | OAuth client/scopes/resource consent; host scopes unchecked and own sandboxes only checked by default.                                                                                                                                         |
| `/{lang}/mcp-login`             | OAuth login handoff preserving the intended authorization flow.                                                                                                                                                                                |

`POST /mcp` is an API endpoint, with no locale prefix or SEO listing. It accepts
agent tokens and OAuth access tokens backed by live grants; it refuses API keys
and cookie-only authentication. `/v1` accepts only API keys. See the
[authentication planes](./guide/auth-planes.md).

Host detail `/{lang}/settings/hosts/{hostId}` also has node-reported **Agent
access** with owner-only lowering and pending status, queued-command review
(Run prepares a wrapper; the person decides whether to press Enter), and recent
metadata-only host audit. Host-access enablement stays node-only.

## Admin Routes

Gated by the `admin` layout, whose guard asks the server's
`isAdminSessionAuthorized` (`packages/api/src/lib/sensitive-session-two-factor-gate.ts`),
the same gate every admin procedure and the API-reference route use
(`apps/web/src/server/admin-route-access.ts`). Anyone it refuses — anonymous,
non-admin, unverified, banned, revoked session, or an admin past the forced-2FA
enrollment grace — gets the router's ordinary 404, not a redirect or "access
denied": the admin tree is hidden, not just protected. Admin data is metadata
only; it never includes commands, output, files or credentials. Namespace `admin`.

## Navigation

Destinations are defined in `apps/web/src/lib/nav-items.ts` and filtered by
audience (`public`, `anonymous`, `authenticated`, `admin`) plus placement
(`desktop`, `mobile`, `userMenu`). The `admin` audience follows
`useShowsAdminNavigation()`, a browser mirror of the server gate (admin role,
verified email, forced 2FA satisfied); the admin link is omitted for everyone
else. Home is `anonymous`: a signed-in user's root
is Sandboxes. Signed-in users have one nav surface per breakpoint:
`primaryNavItems` (Sandboxes · Templates · Activity · Terminals · Settings) as the sidebar
at `md` and up and as the bottom tabs below it; the active item comes from
`primarySectionFor`, so every `/settings/...` page lights Settings. The top bar
carries no signed-in links; Settings and Admin are in the user menu. The
public header offers "Open app" instead of Sign In to a visitor with a
session cookie, see docs/design/shell-rules.md § Public header
